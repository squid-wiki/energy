# 拆透读时钟：COSEM、DLMS 与规范分工

[上一篇](./read-clock.md)走通了读时钟，弄清了每个字节的含义。这一篇不学新报文，还是那几条，只是换五个角度看：

1. COSEM 和 DLMS 分别体现在哪些字节上？
2. 面向对象的设计体现在哪里？
3. 为什么连"连接"也是一个对象？
4. 蓝皮书和绿皮书怎么分工？
5. DLMS 自己发明了什么，又沿用了哪些业内标准？

文中标注"实测"的报文，都来自 Gurux DLMS 模拟器（作为外部测试对象，自带 `crystal.xml` 模板，Wrapper 模式，公共客户端）。真实电表返回的内容会有差异。

## 角度一：COSEM 是名词，DLMS 是动词

先记住一句话：

> **COSEM 定义"电表里有什么"，DLMS 定义"怎么去拿"。**

把读时钟的 GET 请求按归属拆开：

![GET 请求的 13 个字节中，前 3 字节和最后 1 字节属于 DLMS，中间 9 字节的类 ID、OBIS、属性属于 COSEM](/img/dlms/get-bytes.svg)

| 字节 | 含义 | 归属 |
|---|---|---|
| `C0 01` | GET 请求，Normal | DLMS：动作 |
| `C1` | 调用 ID 和优先级 | DLMS：动作的控制信息 |
| `00 08` | 类 ID：8，Clock | **COSEM：对象的类型** |
| `00 00 01 00 00 FF` | OBIS：`0-0:1.0.0.255` | **COSEM：对象的名字** |
| `02` | 属性：2，`time` | **COSEM：对象的哪一项** |
| `00` | 不使用选择性访问 | DLMS：动作的选项 |

翻译成一句话：**DLMS 说"读取"，COSEM 说"Clock 对象的 time"。** DLMS 只负责把这 9 个字节的 COSEM 地址原样运过去，它并不知道什么是时钟。

响应也是一样：

| 字节 | 含义 | 归属 |
|---|---|---|
| `C4 01 C1` | GET 响应，调用 ID 1 | DLMS |
| `00` | 成功 | DLMS |
| `09 0C` | 字节串，12 字节 | DLMS 的数据编码 |
| `07 EA 0B 08 ...` | 这 12 字节按"年月日时分秒"解释 | **COSEM** |

最后这一行最能说明问题。对 DLMS 来说，这只是 12 个字节；只有 COSEM 才规定了它们是年月日。

而 AARQ 和 AARE 从头到尾都没有提到任何对象，**它们完全属于 DLMS**。

### 实验：只换 COSEM 字节，DLMS 不用动

如果这种划分是真的，那么只换名词，动词应该完全不变。下面是实测，每次只改变 COSEM 字节，请求的其他部分一字不差：

| 想读的内容 | 类 ID | OBIS | 属性 | 请求 |
|---|---|---|---|---|
| 时钟的当前时间 | `00 08` | `00 00 01 00 00 FF` | `02` | `C0 01 C1 00 08 00 00 01 00 00 FF 02 00` |
| 时钟的时区 | `00 08` | `00 00 01 00 00 FF` | `03` | `C0 01 C1 00 08 00 00 01 00 00 FF 03 00` |
| 连接对象的状态 | `00 0F` | `00 00 28 00 00 FF` | `08` | `C0 01 C1 00 0F 00 00 28 00 00 FF 08 00` |

这正是分层的价值：想读新数据，只需要查 COSEM，通信代码一行都不用改。

## 角度二：面向对象的设计

上一篇用了"面向对象"的类比，这里看它的完整形态。先看三个数是如何一步步定位到数据的：

![先用类 ID 8 选 Clock 模板，再用 OBIS 选中电表里的时钟对象，最后用属性 2 选中 time，读到当前时间](/img/dlms/object-model.svg)

其中 Clock 接口类相当于这样一份定义（示意，不是真实代码）：

```java
class Clock {                  // class_id = 8
    // 属性，从 1 开始编号
    octet_string logical_name;              // 1  对象名（OBIS）
    date_time    time;                      // 2  当前时间
    long         time_zone;                 // 3  时区
    unsigned     status;                    // 4  时钟状态
    date_time    daylight_savings_begin;    // 5  夏令时开始
    date_time    daylight_savings_end;      // 6  夏令时结束
    integer      daylight_savings_deviation;// 7  夏令时偏移（分钟）
    boolean      daylight_savings_enabled;  // 8  是否启用夏令时
    enum         clock_base;                // 9  时钟来源

    // 方法，同样从 1 开始编号
    adjust_to_quarter();                    // 1  校准到最近的 15 分钟
    adjust_to_measuring_period();           // 2  校准到测量周期
    adjust_to_minute();                     // 3  校准到最近的整分钟
    adjust_to_preset_time();                // 4  校准到预设时间
    preset_adjusting_time();                // 5  设置预设时间
    shift_time();                           // 6  小幅偏移时间
}
```

### 实测：把这个对象的属性读一遍

报文都是同一条 GET，只有最后的属性号在变。响应（实测）如下：

| 属性 | 名称 | 响应中的数据 | 解释 |
|---|---|---|---|
| 1 | `logical_name` | `09 06 00 00 01 00 00 FF` | 字节串，6 字节：自己的 OBIS |
| 2 | `time` | `09 0C 07 E4 06 18 FF 0C 03 33 FF FE B6 00` | 字节串，12 字节：时间 |
| 3 | `time_zone` | `10 FE B6` | `10` 是有符号 16 位整数：-330 |
| 4 | `status` | `11 00` | `11` 是无符号 8 位整数：0 |
| 5 | `daylight_savings_begin` | `09 0C FF FF FF FF ...` | 时间字段全是 `FF`，即未配置 |
| 6 | `daylight_savings_end` | `09 0C FF FF FF FF ...` | 同上 |
| 7 | `daylight_savings_deviation` | `0F 3C` | `0F` 是有符号 8 位整数：60 |
| 8 | `daylight_savings_enabled` | `03 00` | `03` 是布尔值：否 |
| 9 | `clock_base` | `16 01` | `16` 是枚举：1，内部晶振 |
| 10 | 不存在 | 结果 `01 03` | 失败，这个模拟器返回"无权读写" |

可以看到，每个属性的类型都不同，所以响应要带类型标签（`09`、`10`、`11`……），接收方靠它决定如何解析。

### 面向对象概念的对应关系

| 面向对象 | COSEM 中的对应 | 在读时钟中的体现 | 这样设计的好处 |
|---|---|---|---|
| 类 | 接口类，类 ID 为 8 | `00 08` | 所有厂商的时钟结构一致 |
| 实例 | 电表里的对象 | 这块表上的那个时钟 | 同一类可以有多个对象 |
| 对象引用 | OBIS 编码 | `00 00 01 00 00 FF` | 名字与厂商无关 |
| 字段 | 属性 | `02` 是 `time` | 按编号访问，比字段名省字节 |
| getter / setter | GET / SET | `C0` 请求 | 所有对象只用同一种读写方式 |
| 方法调用 | ACTION | 比如调用 `shift_time` | 能表达"校时""拉闸"这类动作 |
| 接口 | 接口类只定义外部能看到什么 | 电表内部怎么存时间，客户端不关心 | 厂商可以自由实现 |
| 访问控制 | 按连接分配属性权限 | 公共客户端能读，但不一定能改 | 同一对象对不同客户端开放不同权限 |

需要注意，这是一种设计思路上的对应。COSEM 并没有像 Java 那样让类互相继承，比如 Register 和 Extended Register 是两个独立的接口类。

### 为什么电表要做成对象

对比一下传统协议的思路，比如"寄存器地址表"：

| | 寄存器地址表 | COSEM 对象 |
|---|---|---|
| 怎么找到时间 | 查这款表的手册，比如地址 `0x1234` | 所有表都是 `0-0:1.0.0.255` |
| 怎么解析 | 手册里写着编码方式 | 接口类定义好，响应还带类型 |
| 想知道表支持什么 | 看手册 | 直接读电表的对象列表（下一节） |
| 增加新功能 | 分配新地址，更新手册 | 增加新对象，通信协议不变 |

另一个容易忽略的细节是：**每个接口类的属性 1 都是 `logical_name`**。所以任何对象都能问"你叫什么"，实测读属性 1 返回的正是它自己的 OBIS。这种统一性让通用工具可以处理所有对象。

另外，从通信角色看，**电表是服务端，抄表系统是客户端**。这和"电表是小设备"的直觉相反，但很合理：对象在电表上，别人来访问它。

## 角度三：连接本身也是一个对象

COSEM 把这种设计贯彻得很彻底：**连客户端和电表之间的"连接"，都被建模成了对象**。

它的接口类是 Association LN（类 ID 15），当前连接的 OBIS 固定为 `0-0:40.0.0.255`。建立连接时报文里的内容，都能在这个对象上找到对应：

![左侧是建立连接时报文中的五项内容，右侧是连接对象的五个属性，两者一一对应](/img/dlms/association-mapping.svg)

下面是实测读到的内容：

| 属性 | 响应中的数据 | 解释 | 对应报文里的什么 |
|---|---|---|---|
| 1 `logical_name` | `09 06 00 00 28 00 00 FF` | `28` 就是十进制 40，自己的 OBIS | — |
| 3 `associated_partners_id` | `02 02 0F 10 12 00 01` | 结构体，2 个元素：`10` 即 16，`00 01` 即 1 | Wrapper 里的客户端地址和服务端地址 |
| 4 `application_context_name` | `02 07 11 60 11 85 ... 11 01 11 01` | 结构体，7 个元素 | AARQ 里的应用上下文，最后的 `1` 是"LN，不加密" |
| 5 `xDLMS_context_info` | 见下文 | 协商出的能力 | InitiateResponse 的内容 |
| 6 `authentication_mechanism_name` | `02 07 ... 11 02 11 00` | 也是一个 OID，最后两位是认证机制的分支和编号 | 本例没有认证，编号为 0 |
| 8 `association_status` | `16 02` | 枚举 2：已连接 | AARE 的结果 |

属性 4 里的结构体，这个模拟器是按 OID 的编码字节逐项放的（`60`、`85 74`……）。别的实现可能写成 `2`、`16`、`756` 这样的数值，读真表时要留意。

属性 5 最直观，协商结果被完整地摆了出来：

```text
02 06                 结构体，6 个元素
   04 18 00 00 10     功能位，24 位：只有 GET
   12 03 40           电表最大接收 PDU：832
   12 FF FF           电表最大发送 PDU：65535
   11 06              DLMS 版本：6
   0F 00              服务质量：0
   09 00              加密信息：空
```

这些内容和 AARE 中的 `5F 1F 04 00 00 00 10`、`03 40`、`06` 正好对应。

这里出现了两个概念的交汇：**AARQ、AARE 是 DLMS 的动作，而这个动作的结果被保存成了一个 COSEM 对象。**

这个对象还有属性 2 `object_list`，内容是当前连接能访问的所有对象及其权限。这就是上一节说的"直接问电表支持什么"，也是后续文章的主题。

还可以反过来验证连接的必要性。不发 AARQ、直接发 GET（实测）：

```text
-> C0 01 C1 00 08 00 00 01 00 00 FF 02 00
<- D8 02 02
```

`D8` 是异常响应（Exception Response），表示电表不处理这条请求。没有连接，就没有访问对象的资格。

## 角度四：蓝皮书和绿皮书的分工

规范的分工和上面的名词、动词划分完全一致：

| 文档 | 回答的问题 | 对应 IEC 标准 | 角色 |
|---|---|---|---|
| **蓝皮书** | 电表里有什么？每种数据的结构？ | IEC 62056-6-1（OBIS）、6-2（接口类） | COSEM，名词 |
| **绿皮书** | 怎么连接、怎么访问、怎么传输、怎么加密？ | IEC 62056-5-3（应用层），以及 4-7、7-6、8-x 等通信配置 | DLMS，动词 |
| 黄皮书 | 怎么证明实现符合规范？ | — | 一致性测试 |
| 白皮书 | 这些术语是什么意思？ | — | 术语表 |

把报文的每一段对应到文档，遇到问题时就知道该查哪本：

| 报文内容 | 去哪里查 | 看什么 |
|---|---|---|
| Wrapper 头 `00 01 00 10 00 01 00 0D` | 绿皮书 | 通信配置，传输层 |
| AARQ、AARE 的结构 | 绿皮书 | 应用层，ACSE 服务 |
| `A1` 里的应用上下文 OID | 绿皮书 | 应用上下文名称 |
| 一致性块的每一位 | 绿皮书 | xDLMS 一致性块 |
| GET 请求的结构 `C0 01 C1 ...` | 绿皮书 | xDLMS 服务 |
| `00 08` 为什么代表时钟 | **蓝皮书** | 接口类列表 |
| `00 00 01 00 00 FF` 为什么代表时钟 | **蓝皮书** | OBIS 编码 |
| 属性 2 为什么是 `time` | **蓝皮书** | Clock 接口类 |
| 12 字节时间的格式 | **蓝皮书** | `date-time` 的定义 |
| 错误码 `03`、`04` | 绿皮书 | `Data-Access-Result` |

一个判断技巧：**问题和具体数据有关，查蓝皮书；和通信过程有关，查绿皮书。**

这样分开的实际好处是，两边可以独立演进。增加一种新的电表数据，只改蓝皮书；增加一种新的通信技术，只改绿皮书，已有的数据模型完全不受影响。

## 角度五：DLMS 沿用了哪些业内标准

DLMS 没有从零发明一切。它自己只定义电表领域特有的部分，通用问题则直接采用成熟标准。

### 在读时钟里用到的

| 用在哪里 | 沿用的标准 | 在报文中的体现 | 为什么不自己发明 |
|---|---|---|---|
| 建立连接 | **ACSE**，ISO/IEC 8649、8650 | AARQ、AARE 的整体结构 | 建立连接是通用问题，OSI 体系早有定义 |
| 描述消息结构 | **ASN.1**，ITU-T X.680 | 规范用它定义 AARQ 等消息 | 业内通用的结构描述语言 |
| 消息编码 | **BER**，ITU-T X.690 | AARQ 中"标签 + 长度 + 值"的结构 | ACSE 本身就规定了这种编码 |
| 规则编号 | **OID**，ITU-T X.660 | `60 85 74 05 08 01 01` | 现成的全球唯一编号体系 |
| 网络传输 | **TCP/IP** | 整个 Wrapper 的承载 | 互联网基础设施 |
| 端口 | **IANA** 注册的 4059 端口 | 客户端连接的端口 | 由互联网端口注册机构统一分配 |

### DLMS 自己定义的

| 内容 | 在报文中的体现 | 为什么要自己定义 |
|---|---|---|
| OBIS | `00 00 01 00 00 FF` | 电表数据的命名是这个领域特有的 |
| COSEM 接口类 | `00 08`、`02` | 电表数据的结构同样是领域特有的 |
| xDLMS 服务 | `C0`、`C4` | 需要针对对象设计的读写操作 |
| A-XDR（IEC 61334-6） | GET 请求的紧凑编码 | 电表的链路很慢，需要比 BER 更省字节 |
| Wrapper | 8 字节头 | 要在 TCP 上表达客户端和逻辑设备的地址 |

### 最精彩的接缝：BER 和 A-XDR 的交界

把 AARQ 的用户信息部分再看一眼：

```text
BE 10                 BER：用户信息
   04 0E              BER：字节串，14 字节
      01 00 00 00 06 5F 1F 04 00 00 00 10 FF FF     A-XDR：InitiateRequest
```

`04 0E` 这个字节串，就是**通用标准和 DLMS 私有内容的分界线**。外层的 ACSE 把里面当成一段不透明的字节，完全不用懂 DLMS；里面的内容改用 A-XDR 编码，只有 DLMS 才解析。

这种编码差异的效果也很直观。GET 请求一共只有 13 字节，因为长度固定的字段都不带标签和长度。如果每个字段都用 BER 的"标签 + 长度 + 值"，每个字段至少多 2 个字节。在每秒只有几百字节的电力线载波上，这个差别很实在。

### 其他场景还会遇到的

| 用在哪里 | 沿用的标准 |
|---|---|
| 串口和载波的链路层 | HDLC，ISO/IEC 13239 |
| 加密算法 | AES，FIPS 197 |
| 认证加密模式 | GCM，NIST SP 800-38D |
| 密钥包装 | AES Key Wrap，RFC 3394 |
| 摘要算法 | SHA-256，FIPS 180-4 |
| 签名和密钥协商 | ECDSA、ECDH |
| 证书 | X.509 |

判断依据很简单：**越靠近电表业务，越是 DLMS 自己定义；越通用的问题，越直接沿用现成标准。**
